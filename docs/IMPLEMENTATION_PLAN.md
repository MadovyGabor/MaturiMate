## 2. SQLite mapping for the `.sq` files

The `.sq` files repeat the design table by table with the same names and columns. Only the types and the constraints SQLite cannot express change.

| PostgreSQL feature in the DDL | SQLite / SQLDelight mapping |
|---|---|
| `smallint`, `integer`, `bigint` | `INTEGER` (`AS kotlin.Int` where useful). |
| `GENERATED BY DEFAULT AS IDENTITY` | Content tables: `INTEGER PRIMARY KEY`, values taken from the content files by the exporter. User tables: `INTEGER PRIMARY KEY` (SQLite assigns the value). |
| `boolean` | `INTEGER AS kotlin.Boolean NOT NULL CHECK (x IN (0, 1))`. |
| `decimal(5,2)` (`target_score`) | `REAL`, rounded to two decimals in the app. |
| `timestamp` | `INTEGER` epoch milliseconds with an `Instant` adapter. |
| `date` | `TEXT` `YYYY-MM-DD` with a `LocalDate` adapter. |
| `time` (`reminder_time`) | `TEXT` `HH:MM` with a `LocalTime` adapter. |
| `varchar(n)`, `text` | `TEXT`. SQLite ignores the length; the importer checks it. |
| `DEFAULT CURRENT_TIMESTAMP` | No default (SQLite would store text). The app sets the value. |
| `CHECK (... IN (...))` and the other checks | Copied as they are. |
| `CHECK (email ~* ...)`, `DATE '1900-01-01'` | Regex: not needed (`app_user` is server-only). Date literal written as `'1900-01-01'`. |
| Partial unique index `uq_topic_root_order` | Supported (SQLite 3.8+), copied. |
| Composite foreign keys (`task_key`) | Supported, copied. |
| `ON DELETE` actions | Supported only with `PRAGMA foreign_keys = ON` on every connection; both drivers set it (step 1.3). |
| Foreign keys from user tables to content tables and to `app_user` | Left out (separate files; no accounts on the phone). Kept on the server. |
| plpgsql functions and triggers | Not ported. The validator checks the same rules before the export. `updated_at` and the other rules of user tables are kept by app code. |
| `COMMENT ON TABLE` | SQL comments. |
| `WITH RECURSIVE` (topic subtree) | Supported. |
| `unaccent` on `tag.name` | Not available; the app normalises the search text in Kotlin. |

## 3. Consistency check against the brief

The design is final, so each point lists how it is met without schema changes.

| Brief requirement | How it is met |
|---|---|
| Stable task identifiers across content updates | 3.1 |
| User data references tasks without cross-file foreign keys | Integer IDs (3.1); no foreign keys in the SQLite user tables. |
| Tasks deactivated, never deleted | `task.is_active`. For `topic` and `learning_unit`, `is_published = false`. Rows stay in the content files and are switched off there; the exporter checks against the previous release that no id disappeared. |
| `content_version` | 3.2 |
| Provenance on tasks | 3.3 |
| Reading passages | 3.4 |
| Task-by-task review and history (roadmap 4.2, 4.3) | 3.5 |
| Exam-style practice with a plain time limit (roadmap 4.1) | 3.6 |
| Outbox and sync | 3.7 |
| Flexible answer data per task | `task_format` catalogue: a new format with an existing `answer_mode` is a new row. |
| VPUS dropped | Not in the design. |
| Teacher mode dropped | `ROLE_TEACHER` stays in the design; the V1 app simply has no teacher features. |

### 3.1 Identifiers

The content IDs are `bigint` identity columns declared `BY DEFAULT`, so explicit values can be inserted. The content source files carry the IDs (`task_id`, `topic_id`, `learning_unit_id`, …), and the importer inserts them explicitly and resets the sequences afterwards. The IDs therefore stay the same in PostgreSQL, the content file and the user database, even after a fresh import.

User rows created on the phone (`attempt`, `activity_log`) get local integer IDs. At the first sync (Milestone 7) the backend inserts them with new server IDs and returns the mapping; the phone then stores the server IDs. Composite-key tables (`user_task_progress`, `user_unit_progress`, `user_subject`) need only the user ID mapping.

### 3.2 Content version

Kept outside the tables: the exporter writes it into `content-manifest.json` (`content_version`, `size_bytes`, `sha256`), and the app keeps a copy of the manifest next to the installed content file, so the installed version is read from that file. The SQLite `user_version` pragma holds the schema version (see section 4).

### 3.3 Provenance

Recorded in the content source files (`source_type`: own, teacher, AI reviewed, public domain; `source_note`; `reviewed_at`) and checked by the importer. It is not imported into the database. Teacher permissions stay in a private record outside the repository.

### 3.4 Reading passages

A passage is the `body_text` of a `SUMMARY` learning unit, directly followed by the `PRACTICE` unit with its tasks in the same leaf topic. Short texts can also stand inside `task.question_text`. The app shows the summary text above the tasks when the units are linked this way (rule in the app, by `sort_order`).

### 3.5 Review and history

`attempt` stores the result of each round (points, time). The task-by-task review is shown at the end of a round from the answers held in memory. Per-task results over time come from `user_task_progress`. A review of an old round, answer by answer, is not part of V1.

### 3.6 Exam-style practice

A `PRACTICE` unit (after its `SUMMARY` passage) run in a timed mode. The time limit is derived in the app from `learning_unit.estimated_minutes`. The attempt is stored as `UNIT_ROUND`.

### 3.7 Outbox and sync

Until accounts exist, nothing leaves the phone, so V1 needs no outbox. For Milestone 7: the phone sends the user rows changed since the last sync (`attempt` and `activity_log` are append-like; `started_at`, `last_answered_at` and `activity_date` show what is new), and the sync state is decided together with the backend in Milestone 7.

## 4. Export step (content files → prebuilt SQLite content file)

**Decided 2026-10-28:** the content files in Git are the source of truth. The exporter builds the content file directly from them, with the same loader and validator as the importer; PostgreSQL is not needed for it. The importer (section 5) fills the server's copy of the content from the same files.

```
              ┌─→ exporter → content.db + content-manifest.json → file hosting / CDN → phone
Files (Git) ──┤
              └─→ importer → PostgreSQL (server copy, needed by the foreign keys of the user tables)
```

A Kotlin/JVM command-line tool in `tools/content-pipeline`. It uses the generated `ContentDatabase` from the shared `:database` module, so the file always matches what the app reads.

1. Create an empty SQLite file with `ContentDatabase.Schema.create(driver)`.
2. Load and validate the content files. Insert the rows in foreign-key order. Tasks, units and topics are never removed from the files; they are switched off (`is_active` / `is_published = false`), so history in the user database never points to nothing. With `--previous <old content.db>`, the exporter fails if any id of the previous release is missing.
3. Set `PRAGMA user_version` to `ContentDatabase.Schema.version` (otherwise the Android driver treats the file as empty).
4. Run `PRAGMA foreign_key_check`, `PRAGMA integrity_check`, `VACUUM`.
5. Write `content-manifest.json`: `content_version` (an integer that only grows, for example `2026102801`), `schema_version`, `size_bytes`, `sha256`.

Rows are written in a fixed order and `created_at` is derived from `content_version`, so the same files give the same hash.

In the app: the file ships in `composeResources/files/`, is copied to app storage on first start, and is opened with foreign keys on. **Content updates (decided 2026-10-28):** the app downloads `content-manifest.json` from file hosting (GitHub Releases or a CDN such as Cloudflare R2); when `content_version` is higher, it downloads the new file to a temporary location, checks size and SHA-256, and swaps it in. No app release is needed for new content, and `user.db` is never touched. This needs no backend and can come before Milestone 7.

## 5. Importer (content files → PostgreSQL server copy)

### 5.1 File format (built in step 1.6, see `tools/content-pipeline/README.md`)

One folder per leaf topic. Lesson text is Markdown, tasks are JSON.

```
content/
  task_formats.json                  # task_format rows
  tags.json                          # tag rows
  HU_MJL/
    subject.json                     # subject_id, code, names, track
    01-stilisztika/
      topic.json                     # topic_id, title, order_index
      01-szokepek/
        topic.json
        10-summary.md                # learning_unit (SUMMARY): front matter + body_text
        20-practice.json             # learning_unit (PRACTICE) + unit_task rows
        tasks.json                   # task, task_option, task_key, task_accepted_answer, task_tag
```

Every field maps to a column of the design. The only extra fields are the provenance fields (3.3), which the importer checks and does not import. Options are referenced by their label in keys; the ids of options, accepted answers and attachments are derived as `task_id * 100 + position` (at most 99 per task). A helper command that reserves the next free ids is not built yet.

### 5.2 Validation (all errors reported together; nothing is written on error)

* Required fields, `CHECK` values and `varchar` lengths of the DDL.
* IDs unique per table across all files.
* Text format: only `**bold**`, `*italic*`, `[[n]]`; anything else (including HTML) is an error.
* Format rules from the design: `MC_SINGLE` one key in slot 1; `TRUE_FALSE` two options; `MATCHING` one key per `PROMPT` option; `ORDERING` one key per position; gap markers `[[1]]…[[n]]` match the slots; `TEXT` formats have accepted answers and no options.
* Structure: tasks and units only on leaf topics; `SUMMARY` has text, `PRACTICE` has tasks; `round_size` not larger than the core tasks; unique sort orders.
* Provenance present for every task and unit.
* `*_private.json` and anything outside `content/` are never read.

### 5.3 Writing

One transaction, upsert by ID, so running it twice is safe. Rows owned by a task and the task list of a practice unit are replaced. Rows that disappeared from the files are deactivated (`is_active`, `is_published`), not deleted. The PostgreSQL triggers stay as a second check. `--dry-run` validates without writing.

## 7. Testing approach

* **Grading:** table-driven tests per format: correct, wrong, partly right slots, `case_sensitive`, spaces, accepted variants.
* **Mappers and queries:** in-memory SQLite on the JVM test target, one test class per repository.
* **Importer:** a valid fixture folder and one failing fixture per validation rule, run against the docker PostgreSQL so the triggers are tested too; a second run changes nothing.
* **Exporter:** export the fixture, open it with `ContentDatabase`, compare row counts; two exports give the same SHA-256; a missing id of the previous release fails.
* **User database migrations (from Milestone 6):** a schema snapshot per released version, `verifySqlDelightMigration`, and a data test per migration.
