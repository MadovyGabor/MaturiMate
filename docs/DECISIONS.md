# Decisions

What was decided and why. Newest first. A decision that changes is not deleted: it is marked *Replaced by* with the date of the newer entry.

## 2026-11-01

* **The user database is used one call at a time.** The repositories and the sign-up setup run their user database work on one dispatcher, `Dispatchers.IO.limitedParallelism(1)` (`AppModul`). Reasons: two transactions at the same time, or a read in the middle of another transaction, lost updates in tests (6 of 300 runs), and a sign-up that moves the guest's rows could come between a save's id and its write; the database is small, so one call at a time costs nothing noticeable. See [review-2026-11-01.md](../llm/review-2026-11-01.md) 3.3.
* **A profile that cannot be read is retried, never treated as a new user.** Reads of the profile are retried three times (100 ms, 0.5 s, 2 s); if they still fail at the start, the app shows an error screen with "Újrapróbálom" instead of the onboarding, and a later failure keeps the screen that is shown. Reason: a passing database error sent a user who had finished the onboarding back to it until the next start.
* **The toolchain is on AGP 9.5 without opt-out flags.** Gradle 9.8.2, compileSdk and targetSdk 37, Compose Multiplatform 1.12.2, Navigation3 1.2.0, Lifecycle 2.11.0, Ktor 3.6.1, Material 3 1.9.0; CI on JDK 21 with the current GitHub Actions. Compose libraries are catalog entries instead of the deprecated `compose.*` aliases, and previews use `androidx.compose.ui.tooling.preview.Preview`. In `:database`, the Android and desktop shared source set selects the Android target by its type, because the hierarchy template's `withAndroidTarget()` does not match the Android-KMP target. Details: [toolchain-agp9.md](../llm/toolchain-agp9.md).
* **The toolchain update comes before the unit engine.** AGP 9 with the module split, Compose Multiplatform 1.12 and the newest libraries become Milestone 6, on their own branch (`chore/toolchain-agp9`); the milestones after it move up by one (the unit engine is now 7, the polish and beta 10, the release 11). Reasons: the split of `composeApp` moves files and build scripts, which is cheapest before the lesson and task screens are added; the onboarding is finished, so a build problem can be told apart from a feature bug; and AGP 10 removes the old Android library plugin, so the move cannot be skipped. Plan: [toolchain-agp9.md](../llm/toolchain-agp9.md). *Moves step 9.0 of the 2026-10-31 roadmap.*
* **One `shared` module and one module per app.** `composeApp` is renamed to `shared` (all UI and features, the expect/actual code, Compose resources); the Android app moves to `androidApp` and the desktop app to `desktopApp`, each holding only its entry point and platform setup. Reasons: the layout JetBrains recommends; AGP 9 requires the Android app to be separate anyway, and doing the desktop at the same time keeps the apps alike, so a later iOS or web app is one more small module. The rename touches the Compose resources imports and every path, so it is a step of its own.
* **Stable versions only.** Every tool and library goes to its newest stable release; no alpha, beta or release candidate, even where JetBrains pairs a stable Compose release with a pre-release library (Material 3 stays on 1.9.0 instead of `1.12.0-alpha03`). Reason: the owner's choice; an alpha would bring changing APIs into a build that should only change its tooling.
* **The exam date follows a rule.** The spring written exams start on the Monday of the second week of March, so `ExamDates.secondWeekWeekday` gives the second Monday of March, and the date step offers it for the next two springs. Reason: the owner's rule; it holds most years, unlike a fixed day. The official date replaces it once it is published (10.6).
* **Fewer labels, larger text on the onboarding.** The "Hamarosan" label is removed from the subject list; "Kötelező" sits under the subject name with a lock, so long names do not break. Descriptions on the onboarding, account and profile screens use `body-large` instead of `body-medium`, and notes `body-medium` instead of `body-small`. Reason: the owner found the screens crowded and the texts small on a phone and on desktop.
* **The exam subjects follow the school's teaching language.** Slovak schools: 2 `SK_SJL`. Hungarian schools: 1 `HU_MJL` and 5 `HU_SJSL` (Slovak language and Slovak literature, its own exam). Both: English as two subjects, 3 `ANJ_B1` and 6 `ANJ_B2`, and 4 `MAT` (Mathematics, optional). One subject is one exam. Reason: Hungarian schools take a different Slovak exam from Slovak schools, and the B1 and B2 English exams have different task types (B2 asks for word forms where B1 asks to choose). Students and learners see one English card with the level question; the level decides which English subject is saved ("Még nem tudom" saves B1). `user_subject.level` is no longer written; the column stays.
* **A teacher picks from both schools' subjects.** A teacher may teach at a Hungarian and a Slovak school, and both English levels, so a teacher gets all six subjects, the own school's first, with English B1 and B2 as two cards. Learners see their own school's subjects only. Reason: the owner's choice.
* **Mathematics is one subject in both languages.** Each task has one id and a Hungarian and a Slovak text; the app shows the teaching language. Reason: the progress stays when the language changes, and a task is written once and translated. The content model for this comes with the unit engine (Milestone 7).
* **Google comes before the consent.** "Folytatás Google-lel" opens Google at once; back in the app the user checks the name from Google and accepts the terms, and only then are the profile, the answers and the consents written to the server. The e-mail sign-up still asks for the consent before the code is sent. The server marks the onboarding finished last, after the answers and the consents. Reason: the owner's choice; and a sign-up that failed half way (the subjects were missing on the server) had already looked finished, so a later sign-in skipped the rest. Supabase Auth creates the account when Google answers; that cannot be avoided.
* **The account buttons work before the consent.** "Fiók létrehozása" and "Folytatás Google-lel" are no longer disabled: without the required consent "Fiók létrehozása" shows a message under the consent box and a snackbar. Reason: on a phone the consent box is below the fold, so a disabled Google button looked broken.
* **The profile changes an answer with the onboarding's own question screen.** The profile tab lists every answer of the user's role (language, role, subjects with the English level, exam date, daily goal, reminder) and the days until the exam; tapping one opens its onboarding question with a plain back button and "Mentés" instead of the step header and "Tovább" (`LocalEditingAnswer`). Reason: one screen and one ViewModel per question, so the onboarding and the profile cannot drift apart. A new role asks for the subjects again, then for an exam date or a daily goal when the new role needs one that is missing. The open main tab survives the rebuild after a language change, so the user stays on the profile. The old profile's subject statistics (mock data) are removed; real statistics come with progress.

## 2026-10-31

* **The account step: consent first, then e-mail or Google.** *(Google part replaced on 2026-11-01: "Google comes before the consent".)* The required consent unlocks both "Fiók létrehozása" and "Folytatás Google-lel". An e-mail sign-up is confirmed with the 6-digit code on the same screen. A Google account that already has a profile on the server is treated as a sign-in. Creating the account and "Körülnézek" both finish the onboarding. The Google button is the one place where a screen uses the Supabase client directly (`rememberGoogleSignIn`), because compose-auth's Google flow is a Composable. The consent sentence names the terms and the privacy notice, which do not exist yet, so it has no links for now.
* **After sign-up or sign-in the guest's rows become the account's, and the profile goes to the server.** `LocalUserProvider.adoptAccount` moves every local row from the guest id to the account id in one transaction (the local half of 7.5). After a sign-up, `AccountSetup` writes the profile, settings, role and subjects to Supabase and records the consents (`TERMS`, `PRIVACY`, `AGE_16`, and `MARKETING` when chosen, document version `1.0`). After a sign-in, the account's profile on the server replaces the answers on the phone. Only these rows are written now; progress sync stays in Milestone 11. The exam subjects are seeded on the server by a migration (`20261101130338_seed_exam_subjects.sql`), because `user_subject` refers to them.
* **The reminder step saves the setting; the notification comes with the streak.** "Bekapcsolom" asks the system for the notification permission (Android 13 and newer) and turns the reminder on only if it is allowed; "Most nem" saves it off. Scheduling the daily notification belongs to the streak (9.1), where it can say something useful. The Android manifest now also declares `INTERNET`, which Supabase needs.
* **The daily goal is empty until it is answered.** The first save creates `user_settings` with an empty `daily_goal_minutes` (the column's default of 10 is not used), so the onboarding can tell an answered goal from an unasked one when it resumes. The screen still preselects 10 minutes.
* **The suggested exam dates are 15 March, as in the prototype.** *(Replaced on 2026-11-01: "The exam date follows a rule".)* `ExamDates.nextSpringExams` offers the next two springs; the day is an example until the official dates are checked, and any other date can be picked from the calendar (today to three years ahead). Dates are written with month names from the app strings (`date_long`, `months`), because kotlinx-datetime has no Hungarian or Slovak names.
* **The onboarding's subject list is a fixed catalogue in the app.** *(The subjects were replaced on 2026-11-01: "The exam subjects follow the school's teaching language".)* `CatalogSubject` lists Hungarian (1 `HU_MJL`, Hungarian schools only), Slovak (2 `SK_SJL`), English (3 `ANJ`, with a level) and Mathematics (4 `MAT`, optional), with their names as app strings. Reason: the onboarding must offer subjects before their content exists (the starter pack has one lesson), and `user_subject` refers to these ids. A subject without installed content gets the "Hamarosan" label. Content written for these subjects uses the same ids and codes. Compulsory subjects are preselected and locked for students only; learners and teachers pick freely.
* **The app language is switched by rebuilding the screens, and the onboarding resumes from the saved answers.** Compose resources take their language from the platform locale; the API to give them another one is internal. So the app sets the platform locale (`LocalAppLocale`, the pattern Compose Multiplatform recommends) and rebuilds the screens with `key()`. Rebuilding resets the navigation, so the onboarding back stack is computed from the saved answers instead of being kept in memory. The same logic gives the resume after a restart (step 5.13).
* **Android minSdk 26, and the session in the library's default storage.** supabase-kt needs Android 8.0 (API 26) unless core library desugaring is set up; nearly every phone in use has it, so minSdk moves from 24 to 26 instead of adding desugaring. The signed-in session is kept by supabase-kt's own storage (SharedPreferences on Android, Java Preferences on desktop), not in the user database, so the library refreshes and restores it without extra code.
* **Toolchain update now, AGP 9 later on its own branch.** Kotlin 2.4.21, Compose Multiplatform 1.11.1, Gradle 9.5.1 and current libraries, because `supabase-kt` 3.8 needs Kotlin 2.4 and Compose 1.11. Compose 1.12 (with Navigation3 1.2 and Lifecycle 2.11) needs AGP 9.1 and compileSdk 37, and Gradle 9.6 or newer does not run AGP 8. AGP 9 no longer allows an Android app and Kotlin Multiplatform in one module, so `composeApp` has to be split into a shared library and a thin Android app module. That restructuring is a separate step (see the ROADMAP), not mixed into the onboarding work.
* **Two columns are added to the user schema.** `user_subject.level` (`B1` or `B2`, empty for subjects without levels) holds the English level, and `user_profile.onboarding_completed_at` marks the end of the onboarding. Reasons: the level belongs to the user's choice of a subject, so it depends on the whole key of `user_subject` (third normal form holds); two separate English subjects would split shared content and turn a level change into a delete and an insert. *(The English part was replaced on 2026-11-01: English is two subjects, `ANJ_B1` and `ANJ_B2`, and `level` is no longer written.)* The onboarding saves after every screen and asks different questions per role, so its end cannot be derived from the other fields; on the server the column also lets a returning user on a new phone skip the questions. *Partly replaces the 2026-10-28 entry "The database design is final".*
* **E-mails carry a 6-digit code, sent through Resend from a subdomain.** Sign-up confirmation and password reset use a code the user types into the app, so no deep links are needed on Android or desktop. Resend (free tier) sends from `maturimate.madovygabor.com`; the website, terms and privacy notice are planned on the same subdomain. Switching to another provider later only changes the SMTP settings in Supabase.
* **Content is not exposed through the Supabase API.** The content tables on the server have row level security without policies; the app gets content only as a file (starter pack, then the download after sign-up). Reason: reading the task bank through the API would bypass the content protection. Only the importer writes these tables.
* **The schema lives in Supabase migrations.** `supabase/migrations` replaces `dbServer/postgres/01_ddl.sql` (a copy of the course design, so it may change). The local Docker database applies the same migrations with a small stand-in for `auth.users`. Changes are new migration files; an applied migration is never edited.
* **Local guest instead of Supabase anonymous accounts.** "Körülnézek" keeps the user's data on the phone only, under a temporary local id; no account is created on the server. After the first lesson, signing up is required, and the local rows move to the new account id. Reasons: the same experience with much less work and risk: no anonymous users on the server, so no identity linking, no CAPTCHA for anonymous sign-ins, no cleanup job and no `is_anonymous` rules; and no personal data reaches the server before the user accepts the terms. Sync only arrives in Milestone 11, so nothing is lost by keeping guest data local. Anonymous sign-ins stay off in Supabase.
* **The guest gate is not a security boundary.** A technical user could skip the required sign-in on their own phone; this only affects themselves, because the server is reachable only with an account and the content on the phone is already readable (see the content protection entry of 2026-10-28). Data that comes from the phone in a later sync is checked on the server.

* **Only a starter pack ships in the app.** The APK contains the first lesson only; the full content file is downloaded after sign-up from private Supabase Storage with a signed link, then works offline. Reason: a modified app (no root needed) could otherwise skip the sign-in and read every lesson from the bundled file, and this would hold even with sign-in required up front. A guest can open only the first lesson. *Refines the content delivery entry of 2026-10-28.*

## 2026-10-30

* **Accounts come with the onboarding rework, not in Milestone 7.** Building the onboarding without them would mean rebuilding it later, and every local row would need a new `user_id`. Supersedes the 2026-10-28 entry "Login and registration come before the Hungarian release" in timing.
* **Sign-in flow:** the onboarding ends with a sign-in screen (Google and e-mail) and a small "Körülnézek" (look around) button. After the first lesson, signing in is required: there is no "later" button. *How "Körülnézek" works was replaced: 2026-10-31 (local guest instead of an anonymous account).*
* **Supabase instead of Neon.** One service for PostgreSQL, authentication and file storage with signed links, so no own API server is needed. Access is protected with row level security policies. Consequence: `user_id` becomes a UUID on the server and on the phone, and `auth.users` replaces the own user and password tables. Check pricing and free-tier limits before creating the project.
* **Onboarding asks:** teaching language (HU/SK), exact graduation date, English level (B1/B2) and daily goal in minutes. Settings move from DataStore to the user database; DataStore is removed.
* **Design system first.** A warm gold, brown and graphite palette on the Material 3 roles, light and dark (the old teal is dropped), Literata and Manrope. [docs/design-system](design-system/README.md) is the source; the Compose theme follows `tokens.json`.
* **One instruction file for all AI tools.** Rules live in `AGENTS.md`; `CLAUDE.md` only imports it. Local notes and AI outputs stay in the gitignored `llm/` folder; lasting decisions go into this file.
* **Small steps.** The roadmap is split into small steps, one change per step, and work is planned and approved before code is written.

## 2026-10-28

* **Content lives in a private repository** (`maturimate-content`), cloned into `content/` inside this repository and gitignored (`/content/`). This repository stays public with code and test fixtures only. Reason: the lessons and tasks are the owner's work and must not be downloadable from the public repository. CI of the public repository never sees real content; the private repository's CI runs the exporter.
* **Content protection, in order:** private content repository now; with login, downloads from private storage through short-lived signed links (optionally Play Integrity), and content split into packs per subject; terms of use and a copyright notice before release; SQLCipher only if copying is seen. Anything on the phone can be extracted by a determined person; the aim is to stop easy downloading.
* **Clean Architecture for the database:** generated SQLDelight classes stay in the data layer; features get domain models, repository interfaces and mappers. The UI never calls the database directly.
* **Content delivery: bundled file plus downloadable updates.** *Refined 2026-10-31: only a starter pack is bundled.* The app ships a prebuilt `content.db`; later it downloads newer versions from private storage (signed links) by `content-manifest.json`. No app release for new content. Reason: offline-first, cheap, no backend needed for content.
* **The content files in Git are the source of truth.** The exporter builds `content.db` directly from the files. The server PostgreSQL holds accounts, progress and a copy of the content, filled by the importer from the same files, because the user tables reference content rows by foreign key. *Neon replaced by Supabase: 2026-10-30.*
* **Content rows are never removed from the files**, only switched off (`is_active` / `is_published = false`). The exporter checks against the previous release.
* **The tools stay in Kotlin**, so the exporter shares the generated database code with the app. The `.sq` files move into a shared `:database` module.
* **The database design is final:** no table or column is added, removed or changed; needs the design does not store are solved in files or in app code. *Partly replaced: 2026-10-30 (UUID user ids and `auth.users` for Supabase); 2026-10-31 (English level and the end of the onboarding).*
* **Login and registration come before the Hungarian release.** `user_profile` (with the required name and date of birth) is written at registration. *Timing replaced: 2026-10-30.*
* **No DataStore work in this phase.** *Replaced: 2026-10-30 (DataStore is removed in the onboarding rework).*
* **The onboarding is redesigned separately.** Its design decides how `user_profile`, `user_settings` and `user_subject` are filled. *Done: 2026-10-30.*
* **Work does not continue on the `database` branch.** A new branch from `main` is used. Reasons: the exam-centred schema is replaced; the branch conflicts with `main` in five files; its history contains `HU_MJL_2025.json` (a digitised official paper). Reused by hand: the SQLDelight Gradle setup and the `DatabaseDriverFactory` files.

## 2026-10-22

* V1 uses only content written for this project. Official NIVAM papers move to V2 and need written permission.
* VPUS/SNI extended time is dropped entirely.
* Teacher mode is dropped.
* Exam-style practice stays in V1, with own tasks and a plain time limit.
* Subject order: Hungarian, Slovak, English (B1/B2), Mathematics.
* The schema may change freely until the first tester installs the app; after that the user database needs migrations.
* Offline-first: server PostgreSQL, read-only content SQLite on the phone, user SQLite on the phone.
