Findings of the code review after Milestone 6 (commit `5dc7119`), grouped by area. For each: what goes wrong, why (the cause in the code), how it is fixed, and the test that proves it. Status: **plan, waiting for the owner's approval**; nothing is fixed yet.

## 1. Errors that are not handled

### 1.1 Crash when the server sends an unexpected value (High)

* **What happens:** signing in to an account whose server profile has a value the app does not know (a new subject level, a malformed date) crashes the Android app.
* **Cause:** `SupabaseAccountRepository.downloadProfile` (`shared/.../auth/data/SupabaseAccountRepository.kt:96-112`) converts the rows with `TeachingLanguage.valueOf`, `SubjectLevel.valueOf`, `LocalDate.parse` and `Instant.parse`, which throw `IllegalArgumentException`; decoding can throw `SerializationException`. Its `call` wrapper (`:115-126`) catches only `HttpRequestException`, `RestException` and its own `NotSignedIn`. `AccountSetupImpl` runs the call in `NonCancellable`, so the exception reaches `viewModelScope`, where nothing catches it.
* **Fix:** `call` catches every `Exception` except `CancellationException` and returns `AuthError.UNKNOWN`. The row conversion is lenient: an unknown enum value becomes null (`entries.firstOrNull { it.name == value }`), an unparsable date is dropped.
* **Test:** `AccountTest`: a mocked server answer with an unknown level and a broken date returns a profile without them, and a garbage answer returns `UNKNOWN` instead of throwing.

### 1.2 An unreadable profile looks like a new user, until the next start (High)

* **What happens:** after one failed read of the profile (a locked or busy database), a user who finished the onboarding sees the onboarding again, in the phone's language, until the app is restarted.
* **Cause:** `AppViewModel` (`core/presentation/AppViewModel.kt:33`) ends the profile flow with `.catch { emit(AppState(language = null, onboardingCompleted = false)) }`. `catch` emits once and the flow completes, so the state never changes again. `OnboardingNavigationViewModel` (`OnboardingResume.kt:42, 48`) does the same.
* **Probable cause of the flaky `AppViewModelTest`:** the ViewModel (Swing thread) and the test (its own thread) call `LocalUserProvider.userId()` for the first time at the same moment on one in-memory connection (see 3.3). When that throws, the `catch` above ends the flow, the language never arrives, and the test times out after 5 seconds. To be confirmed by the test in 3.3.
* **Fix:** the flows retry after an error (`retryWhen` with a short delay, a few attempts) and only then show an error state with a retry button instead of the onboarding.
* **Test:** `AppViewModelTest`: a repository that fails once and then succeeds ends in the right state; the flaky test is run 50 times in a loop.

### 1.2a The onboarding sometimes starts again on the welcome screen after the language (Medium)

*Found while fixing 1.2.*

* **What happens:** after the teaching language is picked, the onboarding sometimes shows the welcome screen instead of the role question. `OnboardingFlowTest.learnerSkipsTheExamDate` failed once in 15 runs, on the committed code as well.
* **Cause:** the new language rebuilds the app at once (`App.kt`, `key(appState.language, …)`), and the rebuilt onboarding takes its first back stack from `OnboardingNavigationViewModel`. That ViewModel outlives the rebuild, and its stack can still come from the profile before the language was saved, so the onboarding starts from the welcome screen.
* **Fix:** the ViewModel gives the stack together with the language of the profile it came from (`OnboardingResumeState`), and the onboarding waits until that language is the one the app was rebuilt with.
* **Test:** `OnboardingResumeTest.aStackFromBeforeTheLanguageChangeIsNotUsed`; `OnboardingFlowTest` ran 30 times without a failure after the fix (1 in 15 before).

### 1.3 Errors that are dropped (Low)

* **What happens:** if saving the end of the onboarding fails, "Tovább" on the last step does nothing and shows nothing.
* **Cause:** `OnboardingNavigationViewModel.finish` (`OnboardingResume.kt:52-54`) ignores the result of `completeOnboarding`.
* **Fix:** show the error snackbar, like the question screens do.
* **Test:** `OnboardingResumeTest`: a failing save shows the snackbar.

### 1.4 Cancellation is swallowed (Low)

* **What happens:** work cancelled because a screen closed comes back as an error instead of stopping.
* **Cause:** `runCatching { load() }` (`OnboardingQuestionViewModel.kt:42`) and `catch (e: Exception)` in `UserProfileRepositoryImpl.save` (`:130`), `ProgressRepositoryImpl.run` (`:123`) and `ContentRepositoryImpl.read` (`:196`) also catch `CancellationException`.
* **Fix:** rethrow `CancellationException` before the general `catch`, as `AuthRepositoryImpl.call` already does.
* **Test:** one repository test: cancelling a save cancels, it does not return an error.

## 2. Sign-in and account

### 2.1 Password reset gets stuck when the new password is refused (High)

* **What happens:** the user enters a correct code and a new password that the server refuses (the same as the old one, or a network error). Trying again says the code is wrong; only a new code helps. In between, the user is signed in, but the phone still has the guest's rows.
* **Cause:** `AuthRepositoryImpl.resetPassword` (`:84-87`) runs `verifyEmailOtp` and `updateUser` as one step. The code is used up and a session created by the first call; when the second fails, `SignInViewModel.onResetPassword` (`:119-130`) runs both again.
* **Fix:** two calls in the repository (`verifyResetCode`, `setNewPassword`). The ViewModel remembers that the code was accepted and, on a retry, only sets the password. Leaving the screen after a verified code signs out again, so no half-finished session remains.
* **Test:** `SignInTest`: a refused new password, then a second password, succeeds without a new code.

### 2.2 The onboarding may continue at the wrong step after signing in (Medium)

* **What happens:** after "Már van fiókom" with an account that has not finished the onboarding, the user may land on the welcome screen or an earlier question instead of the first unanswered one.
* **Cause:** `AppOnboardingNavigation.kt:131-136` reads `navigationViewModel.backStack.value` right after the sign-in. The profile flow behind it updates later, on the IO thread, so the value can still come from the guest's profile. It works today mostly because a new teaching language rebuilds the whole onboarding.
* **Fix:** `AccountSetup.completeSignIn` returns the profile it wrote, and the back stack is computed from it (`onboardingBackStack(profile)`).
* **Test:** `OnboardingFlowTest`: sign in with an unfinished account whose language equals the guest's; the screen shown is its first unanswered question.

### 2.3 A second account takes over the first one's rows on the phone (Medium)

* **What happens:** on the account step, the user signs in with Google account A, goes back, and picks account B. All of A's answers on the phone move to B.
* **Cause:** `LocalUserProvider.adoptAccount` (`:50-54`) moves the rows of whatever id is current, not only a guest's. `adoptAccount` in `Profile.sq:80-91` uses `UPDATE OR REPLACE` for every table.
* **Fix:** rows move only from a guest (`is_guest = 1`). Switching from one account to another keeps the new account's own data: the old account's rows on the phone are removed (they are on the server after a completed sign-up).
* **Test:** `LocalUserProviderTest`: adopting B after A leaves no row of A under B.

### 2.4 The snackbar blocks the buttons (Medium)

* **What happens:** while a snackbar is shown, a second error keeps the button disabled for several seconds, and a question screen stays in "saving".
* **Cause:** `SnackbarController` uses `MutableSharedFlow()` without a buffer. `emit` waits until the collector takes the event, and the collector (`MainScaffoldWrapper`) is busy showing the previous snackbar for about 4 seconds. The ViewModels call `showSnackbar` inside their `busy { }` or `saving` blocks.
* **Fix:** a buffered `Channel` (`Channel.BUFFERED`, `receiveAsFlow()`), so sending never waits. Snackbars still appear one after another.
* **Test:** `SnackbarControllerTest`: two events sent without a collector both arrive, and sending returns at once.

## 3. Data consistency

### 3.1 The server copy of the onboarding answers can be left half written (Medium)

* **What happens:** if the connection drops during sign-up, the server can end up with the profile but without the role or the subjects. A later sign-in downloads this incomplete profile and overwrites the answers on the phone with it, including an empty subject list.
* **Cause:** `SupabaseAccountRepository.uploadProfile` (`:37-72`) writes with six separate requests; the role and the subjects are first deleted and then inserted again. There is no transaction across requests.
* **Fix:** one Postgres function, `save_onboarding(...)`, that writes the profile, settings, role and subjects in one transaction for `auth.uid()`; a new migration in `supabase/migrations`, with its row level security tests. The app calls it through `postgrest.rpc`. Also, `AccountSetupImpl.write` keeps the local answer when the server's is empty.
* **Test:** `rls_test.sql`: a user can call it only for themselves; `AccountTest`: the app sends one call.

### 3.2 Consents are recorded twice after a retry (Medium)

* **What happens:** when the last step of a sign-up fails and the user tries again, the terms, privacy and age consents are stored a second time.
* **Cause:** `recordConsents` (`:82-86`) inserts every time, and `user_consent` has no unique constraint.
* **Fix:** in the same migration, duplicates already on the server are removed (the oldest row stays), then a partial unique index on `(user_id, consent_type, document_version) WHERE withdrawn_at IS NULL` is added, and the app inserts with `ignoreDuplicates`. The column types stay: the schema uses `timestamp` everywhere except `onboarding_completed_at`; moving all of them to `timestamptz` would be a separate decision.
* **Test:** `rls_test.sql`: a second identical consent is ignored; a withdrawn one can be given again.

### 3.3 The local user id is not thread safe (Medium)

* **What happens:** a save that runs while a guest signs up can write to the old guest id, and that row is lost. The first start can run two transactions at the same time (and very probably makes `AppViewModelTest` flaky, see 1.2).
* **Cause:** `LocalUserProvider.cached` is a plain `var` (`:27`) and `userId()` has no lock. `UserProfileRepositoryImpl.save` (`:123`) reads the id *before* its transaction, so `adoptAccount` can run in between.
* **Confirmed:** a stress test of the `AppViewModelTest` setup failed in 6 of 300 runs: "cannot start a transaction within a transaction" (two threads in one transaction on the shared test connection), or a read in the middle of another thread's transaction that missed the update.
* **Fix:** every call to the user database runs on one dispatcher that runs one call at a time (`Dispatchers.IO.limitedParallelism(1)`, `AppModul`): the repositories and the sign-up setup (`AccountSetupImpl`). The cached id is `@Volatile`, and `save` creates the guest id first and reads the id again inside its transaction.
* **Test:** `AppViewModelTest.aSaveRightAfterTheStartAlwaysArrives` (100 runs with the app's setup); `LocalUserProviderTest.savesDuringASignUpEndUpUnderTheAccount`.

### 3.4 Desktop: "database is locked" on parallel writes (not a bug)

* **Checked:** the desktop driver opens one connection per thread, but sqlite-jdbc waits 3 seconds for a busy database by default, so parallel writes do not fail. A test with 200 writes from 8 threads passes without any change (`UserDatabaseFileTest`); it stays as a guard. Since 3.3, the app's writes run one at a time anyway.

## 4. Security

### 4.1 The Android backup contains the sign-in session (High)

* **What happens:** Android's automatic backup copies the app data to Google Drive, including the supabase-kt session (with its refresh token) and the user database. Restored on another phone, the user is signed in there without signing in.
* **Cause:** `androidApp/src/main/AndroidManifest.xml:11` has `android:allowBackup="true"` without backup rules.
* **Fix:** backup rules (`dataExtractionRules` for Android 12 and newer, `fullBackupContent` for older versions) that leave out the session's SharedPreferences; the user database may stay in the backup. To be checked on a phone with `adb shell bmgr`.
* **Test:** manual backup and restore on a phone (written down in the step).

## 5. Performance and size

### 5.1 The release build is not shrunk: 28.5 MB APK (High)

* **What happens:** the APK is 28.5 MB with 80 MB of uncompressed dex code, which means a slow download, more storage and a slower first start.
* **Cause:** `isMinifyEnabled = false` in `androidApp/build.gradle.kts`, so R8 removes nothing. Most of the code is `material-icons-extended` (thousands of icons), of which the app uses 25.
* **Fix:** for release, `isMinifyEnabled = true` and `isShrinkResources = true`, with keep rules for kotlinx-serialization (navigation routes, Supabase rows), supabase-kt, Ktor and SQLDelight. If R8 cannot remove the icons well enough, the 25 icons are copied as vectors and the dependency goes.
* **Test:** size of the release APK before and after; the whole app checked on a phone with a release build (sign-in, onboarding, content).

### 5.2 The profile is read again for every screen that watches it (Low)

* **What happens:** after every save, the same three profile queries run once for each watcher (the app, the onboarding navigation twice, the profile screen, the open question).
* **Cause:** `UserProfileRepositoryImpl.profile` is a cold flow; each collector starts its own queries.
* **Fix:** share it in the repository (`shareIn` on an app scope, `WhileSubscribed(5000)`, replay 1).
* **Test:** the existing profile tests; a counter on the queries in one test.

### 5.3 Content files are read whole into memory (Low, Milestone 11)

* **What happens:** nothing yet (the starter pack is 150 KB). A downloaded full content file of several MB would be read into memory twice.
* **Cause:** `ContentDatabaseProvider` reads the file with `Res.readBytes`; `FileContentStorage.sha256` formats every byte separately.
* **Fix:** with the download in step 11.2: stream to a temporary file, hash while writing, and delete old `-wal`/`-journal` files before the swap. Noted there, not fixed now.

## 6. Code quality and tests

### 6.1 Dead code (Low)

Left from the old onboarding: `DatePickerField`, `MaturitaValidator` with its Koin entry and `MaturitaDateErrorMapper`, `EditDialog` (only its preview uses it), `LocalUserProvider.isGuest` (only tests), possibly `profileSetup/components/LanguageCard` and `LanguageSelector`; the "Hello, World!" preview in `MainFrame.kt:121`; the empty `commonTest/ComposeAppCommonTest.kt` (it also causes the AGP warning about Android host tests). Each is checked for callers before it is removed.

### 6.2 A role read without observing it (Low)

`AppOnboardingNavigation.kt:82` reads `navigationViewModel.role.value` during composition. It works only because every navigation recomposes the screen. Fix: `collectAsState()`.

### 6.3 Old screens break the design system rules (Low, Milestone 7)

About 59 lines with fixed colours, sizes or corner radii in the old screens (`StatickUiSettings`, `ExamSelectionScreen`, `SubjectListTabScreen`, `SurfaceContainer`, `LoadingScreenWrapper`, `AlertDialog`). These screens are rebuilt in Milestone 7, so they are not touched now.

### 6.4 Missing tests and coverage

* Every fix above comes with its test.
* Untested today: `MainFrameNavigationState` (tabs and their back stacks), `AccountRules`, `LocalAppLocale`, `OnboardingNavigationViewModel` on its own.
* Android: no instrumented test at all. A few `androidDeviceTest` tests for the Android parts: the SQLite driver and the content install, the notification permission, the app language.
* Coverage: Kover for `shared` and `database`, its report in CI, and a minimum for the data and domain code (to be set after the first report; 80% as a starting point). Compose screens and platform calls are not counted towards it.

Rules for the work:

* **Fix the cause, and improve where it helps.** Where the code around a bug is weak (for example the error wrappers that repeat in every repository), it is improved in the same step, as long as the behaviour the user sees stays the same apart from the fix.
* **Dead code** is removed only when nothing in the app uses it: each item is searched for callers (code, Koin modules, tests, previews) and the app is built after the removal. Anything still used stays and is listed in the report.
* **Every fix has a test** that fails before the fix and passes after it, where a test can show it; the backup (4.1) and the release build (5.1) are checked on a phone instead.
* **The Supabase migration** (6a.3) is a new file; applied migrations are not edited. It is applied to the live project only after the owner's go.
